# 07 · 文档规划与路线图（含后续阶段步骤）

> 版本：v1.0（2026-11-12）｜负责人：Lead｜状态：定稿
> 配套：开源仓 `sandai-ascend-migration-docs`（脱敏文档仓）｜CHANGELOG / ROADMAP 见仓内
> 本文回答两件事：**① 文档怎么管（编号/分层/状态/质量门）② 后面阶段怎么走（步骤/出口/产出哪份文档）**

---

## 1. 为什么专门规划文档

项目剩余步骤多（迁移实现 → 真机验证 → 性能 → 稳定性 → 交付），且参与者会换人。文档如果只是"随手写一个 md"，三个月后会出现：

- 同一口径两个说法（例：编码器输出 `C=1024` 还是 `4096`，文档间曾冲突）；
- 新人不知道先看哪份、哪些已作废；
- 验收时找不到"当时凭什么判定通过"的证据链；
- 对外发布时把客户 IP/账号/合同细节泄出去。

所以文档要像代码一样：**有目录、有编号、有状态、有评审、有变更记录、有质量门**。

## 2. 文档分层（L0–L4）

| 层 | 名称 | 回答什么问题 | 读者 | 生命周期 |
|---|---|---|---|---|
| **L0** | 决策与计划层 | 做什么、为什么、什么顺序、缺什么 | 管理层/客户/全员 | 随阶段滚动更新 |
| **L1** | 规范层 | 按什么标准做（评测口径、编码/文档规范、错误码约定） | 实施者 | 定稿后只增补 |
| **L2** | 操作手册层（Runbook） | 具体怎么一步步做（搭建、迁移、验证、发布） | 执行者 | 随工具版本更新 |
| **L3** | 记录与报告层 | 做了什么、结果如何、是否达标（实验记录、评测报告、问题登记） | 评审者/验收方 | **只增不改**（追加式） |
| **L4** | 归档层 | 某里程碑的完整快照与签收 | 验收/审计 | 冻结 |

> 判断落层只需问一句：**"这份文档如果明天事实变了，是改写（L0/L1/L2）还是新开一份（L3/L4）？"**

## 4. 每份文档的元数据头（强制）

```markdown
# <编号> · <标题>
> 版本：vX.Y（YYYY-MM-DD）｜负责人：<name>｜状态：草稿 | 评审中 | 定稿 | 已归档
> 关联：<上游文档>｜证据：<数据/日志/代码路径>｜对应任务：<T-xxx / DOC-xxx>
```

**状态机**：

```
草稿 ──评审通过──► 评审中 ──批准──► 定稿 ──里程碑冻结──► 已归档
  ▲                    │
  └──────退回修改──────┘
```

规则：
- **L0/L1/L2** 可改写，但每次改写要 bump 版本 + 写 CHANGELOG；
- **L3/L4** 不改写：新结论 = 新文件（文件名带日期/序号）；
- 任何"删掉结论"的改动，必须在 CHANGELOG 写原因。

## 8. 开源仓发布策略（脱敏）

**进仓**：L0/L1/L2 的通用内容（计划、规范、手册、评测方法、路线图）。
**不进仓**：客户 IP/账号/密码/主机名、合同原文与甲方便签、甲方数据与 MD5 清单明文、原始日志、模型/库文件、内部人员信息、成本与人天报价。

**脱敏规则（自动执行，`scripts/build_open_repo.py`）**：

| 类型 | 规则 |
|---|---|
| IPv4 / 端口 | → `<GPU_HOST>` / `<JUMP_HOST>` / `<PORT>` |
| 用户名 | → `<user>`；跳板账号 → `<jump_user>` |
| 公司/客户名 | → `客户` / `甲方` |
| 密码/token | 一律删除（并加 CI 检查） |
| 绝对路径含用户目录 | → `~/...` |
| 合同金额/人天报价 | 删除 |

**质量门（每次同步必过）**：① 敏感词扫描 0 命中 ② 所有文档有元数据头 ③ 内部链接可解析 ④ CHANGELOG 已更新。
**版本**：`v<阶段>.<修订>`，例：阶段一发布 `v0.1.0`；阶段二真基线后 `v0.2.0`。
