## 3. 环境打通步骤（E0–E5，全部可自行完成）

> 纪律：只在 `GPU4` 上跑；只写 `~/sandai_baseline`（不碰 HDJY 目录）；`apt` 只装缺失的系统库；**任何安装/写入前先向用户报备**（当前待评审）。

| 步骤 | 动作 | 关键命令（Linux） | 产物/判据 |
|---|---|---|---|
| **E0** | 建独立工作目录 + 上传源码 | `mkdir -p ~/sandai_baseline/{src,models,data,baseline,build,logs}`；从本工作区 `10_源码` 传源码（`scp`/base64 小包） | 目录就绪；源码 SHA256 与本机清单一致 |
| **E1** | 系统库 | `sudo apt-get install -y libsodium-dev`（内网源） | `libsodium.so` 可链 |
| **E2** | Python 环境（独立 venv，不动系统环境） | `python3 -m venv ~/sandai_baseline/venv`；`pip install -U pip`；`pip install onnx numpy`；`pip install torch==2.4.1 --index-url https://download.pytorch.org/whl/cu124` | `torch.cuda.is_available()` 在 GPU4 上可 True |
| **E3** | TensorRT 8.6.1.6（CUDA 12.x 版） | 下载 `TensorRT-8.6.1.6.Linux.x86_64-gnu.cuda-12.0.tar.gz`（NVIDIA 公共下载），解包到 `~/sandai_baseline/trt` | `trtexec` 可执行；`libnvinfer.so` 存在 |
| **E4** | 编译原始工程 | `cmake -DSM=80 -DTENSORRT_DIR=... -DTorch_DIR=$(python -c "import torch;print(torch.utils.cmake_prefix_path)") -Dpybind11_DIR=... -DSODIUM_DIR=... -DFASTDECODE_DIR=...`；`make -j32` | `libsandai-basecall.so` + `samples/test_sandai-basecall` |
| **E5** | 替换层 + 全链路 smoke | 假数据 npy + 假 engine（用统一加密流程加密）+ stub `libHDJY-FD.so` → `test_sandai-basecall 4 256 <fake.engine> <fake.npy> 10 out_*.npy` | E-2/E-3 达标 |

**编译要点（来自源码审计，避坑）**：
- `-DSM=80` 必须显式给（A800 = sm_80；默认列表含 80，但显式更稳；**不需要** 4090 的 `-DSM=89`）；
- `SODIUM_DIR`、`FASTDECODE_DIR` 脚本 `build_linux.sh` 没传，必须手动给，否则 `find_package(... REQUIRED)` 直接 fail；
- `version.h` 会写进源码树（`CMakeLists.txt:92-95`）→ 源码目录要可写，或改到 build 目录；
- `md5.cpp` 用 `popen("md5sum|cut")` → 目标机需 coreutils（有）；
- 已知 3 处代码问题（调试 D2H 同步 `sandai-core.cpp:272-316`、吞错误码 `sandai-basecall.cpp:113-123`、`clip` 的 size 语义）→ 一阶段先**不修**，只记录（避免引入变量），真基线后再修。

## 4. 替换层设计：真件到位后"只换文件、不改代码"

### 4.1 目录契约

（目录结构见各章节说明）

### 4.2 三个替换点

| 替换点 | 现状（占位） | 真件到位后 | 切换方式 |
|---|---|---|---|
| **编码器模型** | 假 engine：用 TensorRT 从随机权重 ONNX 生成 `[256,1,5000]→[256,1000,4096]` 的 fp16 engine，并用统一加密流程加密成与真件同格式 | HDJY `.engine`（加密） | `baseline.env` 里 `ENCODE_ENGINE=` 指向 real/ 同名文件；**代码零改动** |
| **解码器** | stub `libHDJY-FD.so`：实现 `host_back_guide_step / host_beam_search_step / host_compute_posts_step / host_run_decode` 四个符号，按 ABI 填充确定性输出（argmax→sequence/qstring/moves） | HDJY 真 `libHDJY-FD.so` | `FASTDECODE_DIR=` 指向 real/lib；**代码零改动**（ABI 逐字节不变） |
| **输入数据** | 合成 npy：`float32 [256,5000]` 随机/构造信号 + manifest | HDJY `.ccf` → npy 转换结果 | `DATA_NPY=` 指向 real/；转换器按格式规范实现 |

> 关键点：**替换的是"文件/路径"，不是代码分支**。`baseline.env` 里三行路径就是"真/假"开关，避免"先写死假后端、后来又要改代码"的返工。

### 4.3 判定与防呆

- `verify_inputs.sh`：对 `models/`、`libs/`、`data/` 生成/校验 SHA256 清单 → 跑基线前先确认"用的是假件还是真件"，报告里自动标注（防止拿假数据的结果当"真基线"交付）。
- `run_baseline.sh` 输出头部固定打印：`MODE=fake|real`、engine SHA256、so SHA256、data SHA256、GPU id、batch、chunk、iterations。
- 精度基线只在 `MODE=real` 且输入为 HDJY MD5 数据时才算有效（写入报告模板）。

## 5. 剩下到底缺什么（聚焦一阶段；按"能不能自己解决"排序）

> 之前说"只缺 .engine 和 .so"，是在**假设数据、环境、依赖都现成**的前提下。实测后完整缺口如下——**只有第 1 项和一阶段无法替代**，其余都能自己搞定。

### 5.1 🔴 必须 HDJY/业务提供（一阶段仅 3 项）

| # | 项 | 为什么一阶段就要 | 不提供时团队能到哪一步 |
|---|---|---|---|
| **A1** | **<N> 个 `.ccf` 测试数据**（<M> 物种，MD5 见合同） | 性能/精度**有效基线**的唯一数据源（合同锁定 MD5） | 只能用合成数据跑通流程，得到"假基线"（E-2/E-3 可达成，E-4 的数值不可交付） |
| **A2** | **`.ccf` 格式规范 / `→npy` 转换规则**（chunk 边界、有效长度、信号归一化、补零） | SDK 入口是 `float**`，仓库无 `.ccf` 解析 | 同上；且无法把 HDJY 数据喂进 SDK |
| **A3** | **加密 `.engine`**（至少 sup 档） | 真实 logits 的唯一来源 | 假 engine 只能验证"链路通"，精度基线无意义 |
| **A4** | **`libHDJY-FD.so`**（4 个 `host_*`） | 真实 sequence/qstring 的唯一来源（stub 只能证明链路通） | 可先出 logits + stub 序列，不能作为精度基线 |

> A1–A4 即"HDJY 提供 .engine/.so"之外**新增的三项**：数据、数据格式、以及 engine 的配套（`calib json`，见下）。**其余都在团队控制内。**
