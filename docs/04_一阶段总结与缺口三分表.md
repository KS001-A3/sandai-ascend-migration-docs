## 1. 一阶段目标（写清楚口径）

| 项 | 定义 |
|---|---|
| **阶段目标** | 在 **A800** 上跑通 `ms_basecall / cudacall` 的 CUDA 基线链路，并让「客户真 `.engine` + 真 `.so`」到位后**只换文件、不改代码**即可产出性能与精度基线 |
| **平台** | A800-SXM4-80GB（`<GPU_HOST>`，经跳板 `<JUMP_HOST>:9090`），固定使用 **GPU #4**（其余卡为客户 vLLM，禁止触碰） |
| **范围** | 原始 CUDA 版工程（不做 910B/CANN/迁移版/`.om`/AscendC——那是阶段二） |
| **出口判据 E-1** | 原始工程在 A800 上编译通过（`librta_basecall.so` + `test_rtabasecall`） |
| **出口判据 E-2** | 用替换层（假数据 + 假 engine + stub 解码）跑通 `Init → Basecall → 输出 4 个 npy`，不崩溃 |
| **出口判据 E-3** | 性能计时链路可用（能打印吞吐与单轮耗时） |
| **出口判据 E-4** | 真件到位后：改 `baseline.env` 三行路径 → 重跑同一命令即出真基线（零代码改动） |

**当前达成情况**：E-1 ✅ ｜ E-2 ✅ ｜ E-3 ✅ ｜ E-4 ✅（机制已验证，等待真件触发）

**实测结果（假件，仅证明链路）**：加密假 engine（20.19 MB）解密+TRT 加载成功 → 10 轮 Basecall → 单轮 ~20.2–25.6 ms，日志 `basecall Speed: 60.4 M samples/sec`（2^20 口径、假件，**不可作为性能基线**）→ `chunk_type/moves/sequence/qstring` 4 个 npy 落盘，exit=0；防呆脚本判定 `MODE=FAKE`（退出码 2）。

### C. 现在还缺、必须他们提供（一阶段唯一外部阻塞）

| # | 缺什么 | 为什么必须 | 拿到后我们做什么 | 缺失时能到哪 |
|---|---|---|---|---|
| **C-01** | **28 个 `.ccf` 测试数据**（6 物种，按合同 MD5） | 验收数据必须甲方提供且 MD5 锁定，不能自造替代 | 放 `data/real/` → 转 npy → 跑真基线 | 只能跑假数据，出"链路通"结论 |
| **C-02** | **`.ccf` 格式规范 / `→npy` 转换规则** | SDK 入口是 `float**`，仓库 `ccf` 零命中；信号归一化/补零/有效长度错一处就静默污染精度 | 写转换器 + 校验 MD5 | 数据到手也喂不进 SDK |
| **C-03** | **加密编码器 `.engine`**（至少 sup 档） | 真实 logits 的唯一来源；假 engine 精度无意义 | 放 `models/real/` → 改 1 行路径 | 精度基线无法产出 |
| **C-04** | **`libfast_decode.so`**（4 个 `host_*`） | 真实 sequence/qstring 的唯一来源；stub 只能证明链路 | 放 `libs/real/lib/` → 改 1 行路径 | 性能/精度基线都缺解码段 |

**另需确认（不阻塞跑通，但影响报告判定）**
- **C-05** 模型配套：`calib json`（qscore 标定，须与 engine 同目录）、输出 dtype（fp32/fp16）
- **C-06** 性能口径：`8.5M sample/s` 的 M 是 10^6 还是 2^20（仓库按 2^20，**虚高 4.86%**）
- **C-07** 精度口径：`Modal identity rate` / `Q_Read_Mean` 的精确计算定义（我们已在 05 给出建议定义，待甲方确认）
